# Журнал взаимодействия с ИИ (Лабораторная работа №1)

## Задание

Провести анализ предметной области «Система учёта заявок Helpdesk»

## Текст промпта (что я написал в ИИ)

"Ты — аналитик. Проведи анализ предметной области «Система учёта заявок Helpdesk» для учебного заведения.
Система должна позволять регистрировать обращения, хранить сведения о заявителе, категории и статусе,
назначать исполнителя и контролировать выполнение. Составь список из 4 ролей (администратор, оператор,
исполнитель, заявитель) с описанием их прав. Сформулируй минимум 14 функциональных и 7 нефункциональных
требований в формате «Система должна…». Определи 5 ключевых сущностей. Составь Use Case диаграмму
(текстовое описание акторов и прецедентов)."

## Ответ ИИ (вставьте сюда ответ)

2.1 Роли пользователей:

| Роль | Права и обязанности |
| ---- | ------------------- |
| **Администратор** | Управление пользователями (создание, редактирование, блокировка), настройка категорий и SLA, мониторинг всей системы, управление отчётами |
| **Оператор** | Приём заявок от заявителей, назначение исполнителей, контроль сроков, изменение статусов, фильтрация и просмотр всех заявок |
| **Исполнитель** | Получение назначенных заявок, изменение статусов, добавление комментариев, отметка о выполнении |
| **Заявитель** | Создание заявок, просмотр своих заявок, добавление комментариев, отслеживание статуса |

### 2.2 Функциональные требования (14)

**FR-01:** Система должна позволять регистрировать новые заявки с указанием заголовка, описания, категории и приоритета.

**FR-02:** Система должна хранить информацию о заявителе (ФИО, email, телефон, роль).

**FR-03:** Система должна обеспечивать аутентификацию пользователей (вход по логину/паролю).

**FR-04:** Система должна разграничивать доступ к функциям в зависимости от роли пользователя.

**FR-05:** Система должна позволять администратору создавать и редактировать категории заявок.

**FR-06:** Система должна позволять оператору назначать исполнителя на конкретную заявку.

**FR-07:** Система должна позволять изменять статус заявки («Новая», «Назначена», «В работе», «Выполнена», «Закрыта»).

**FR-08:** Система должна позволять заявителю просматривать только свои заявки.

**FR-09:** Система должна позволять исполнителю просматривать только назначенные ему заявки.

**FR-10:** Система должна поддерживать добавление комментариев к заявке (с указанием автора и времени).

**FR-11:** Система должна уведомлять заявителя о изменении статуса его заявки.

**FR-12:** Система должна обеспечивать поиск и фильтрацию заявок по статусу, категории, дате и исполнителю.

**FR-13:** Система должна поддерживать контроль SLA (время реакции и время решения для каждой категории).

**FR-14:** Система должна генерировать отчёты по заявкам (количество, среднее время решения, статистика по категориям).

### 2.3 Нефункциональные требования (7)

**NFR-01:** Система должна обеспечивать время отклика интерфейса не более 2 секунд для типовых операций.

**NFR-02:** Система должна поддерживать одновременную работу не менее 50 пользователей.

**NFR-03:** Система должна хранить данные не менее 5 лет без потери информации.

**NFR-04:** Система должна предоставлять удобный интерфейс для работы на компьютерах и мобильных устройствах.

**NFR-05:** Система должна быть интегрирована с корпоративной системой аутентификации (Active Directory).

**NFR-06:** Система должна обеспечивать ролевую модель доступа с разграничением прав.

**NFR-07:** Система должна поддерживать протоколирование действий пользователей (аудит-лог).

### 2.4 Ключевые сущности (5)

1. **Пользователь (User)** — хранит информацию о пользователях системы.
2. **Заявка (Request)** — основная сущность, содержит информацию о проблеме/обращении.
3. **Категория (Category)** — классификация заявок (IT, бухгалтерия, административные вопросы).
4. **Статус (Status)** — состояние заявки (Новая, Назначена, В работе, Выполнена, Закрыта).
5. **Комментарий (Comment)** — сообщения, связанные с заявкой.

### 2.5 Use Case диаграмма (текстовое описание)

**Акторы:**

- Заявитель
- Оператор
- Исполнитель
- Администратор

**Прецеденты (Use Cases):**

1. **Создать заявку** — заявитель создает новое обращение.
2. **Просмотреть свои заявки** — заявитель смотрит статус своих обращений.
3. **Назначить исполнителя** — оператор назначает сотрудника на заявку.
4. **Принять заявку в работу** — исполнитель берет назначенную заявку в работу.
5. **Изменить статус заявки** — исполнитель или оператор меняют состояние заявки.
6. **Добавить комментарий** — все участники могут комментировать заявку.
7. **Управлять категориями** — администратор добавляет/редактирует категории.
8. **Управлять пользователями** — администратор управляет учетными записями.
9. **Просмотреть отчёты** — администратор и оператор видят статистику.
10. **Закрыть заявку** — заявитель или оператор закрывают заявку после решения.
